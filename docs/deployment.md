# Deployment

The live site at [cyberisrael.net](https://cyberisrael.net) is a Cloudflare Worker that
serves the built SPA and gates `/oauth/*` for the CMS sign-in. Cloudflare builds and
deploys it straight from this repository — there is no GitHub Action and nothing to run
by hand.


## How a push becomes a deployment

Cloudflare Workers Builds watches the repo and runs one of two commands depending on
the branch:

| Branch | Command it runs | Effect |
| --- | --- | --- |
| `main` (production branch) | **Deploy command** — `npx wrangler deploy` | Goes live on cyberisrael.net |
| Any other branch | **Version command** — `npx wrangler versions upload` | Uploads a preview version, **never** touches production |

That split is the whole answer to "keep building non-main branches, but only deploy
`main`". Branches still get built, so a broken build is caught before merge, but only
the production branch can change the live site.

The CMS is pointed at `dev` for exactly this reason: an editor publishing an article
lands it on a preview build, and a maintainer still has to review and merge the
`dev` → `main` pull request before it goes live. See [articles.md](./articles.md).

## Where configuration lives

**`wrangler.jsonc` is the source of truth.** Worker name and entry point, compatibility
date and flags, observability, and the static-asset behaviour (including the SPA fallback
and which paths reach the Worker first) all live there, in code, in review.

The Cloudflare dashboard should hold only the things that *cannot* live in a file:

- the Git connection
- the production branch (`main`)
- the three build commands
- the custom domain (see below)
- the CMS secrets (see below)

### The SPA fallback runs before the Worker

`not_found_handling: "single-page-application"` is handled by Cloudflare's asset layer,
which sits *in front of* the Worker. Any browser navigation to a path that isn't a real
file gets `index.html` back and the Worker is never invoked — so a Worker route like
`/oauth/auth` silently disappears.

`assets.run_worker_first` lists the paths that must reach the Worker anyway:

```jsonc
"run_worker_first": ["/oauth/*"]
```

This is easy to miss because `curl` does **not** reproduce it: without a browser's
`Sec-Fetch-Mode: navigate` header the asset layer skips the SPA fallback and the request
falls through to the Worker, so the route appears to work either way. Verify Worker routes
with a real browser navigation, or at least with those headers set:

```bash
curl -I -H 'Accept: text/html' -H 'Sec-Fetch-Mode: navigate' http://127.0.0.1:8788/oauth/auth
```


### The custom domain is the one setting still held only in the dashboard

`cyberisrael.net` is attached to the Worker through Settings → Domains & Routes, so
nothing in this repo records which Worker actually serves the site. That is worth
fixing, because it is the exact gap that made the original incident confusing: a deploy
can succeed on a duplicate Worker and change nothing on the live site.

To move it into code, first confirm in the dashboard that `cyberisrael.net` (and `www`,
if it is used) is attached to **`cyberisrael-website`**, then add:

```jsonc
"routes": [{ "pattern": "cyberisrael.net", "custom_domain": true }]
```

Do not add this from memory. If the pattern doesn't match what the dashboard actually
has, the deploy will fail or move the domain — verify first, then commit.

The commands must stay bare:

```
Build command     npm run build
Deploy command    npx wrangler deploy
Version command   npx wrangler versions upload
Root directory    /
```

> [!WARNING]
> **Never add flags to the dashboard commands.** A flag like `--assets=./dist` or
> `--compatibility-date=...` silently *overrides* `wrangler.jsonc`. The file then says
> one thing, production does another, and nothing in the repo reveals the difference.
> This has already bitten us: the deploy command carried
> `--assets=./dist --compatibility-date=2026-08-31` while the file pinned a newer date,
> and once the Worker entry point was added the hardcoded `./dist` pointed at the wrong
> folder entirely — the build emits `dist/client` now, not `dist`. If you need to change
> deploy behaviour, change `wrangler.jsonc`.

### Why the assets path is not configured anywhere

`@cloudflare/vite-plugin` writes a ready-made config during `npm run build`
(`dist/cyberisrael_website/wrangler.json`, whose `assets.directory` points at
`dist/client`) and leaves a pointer in `.wrangler/deploy/config.json`. Plain
`npx wrangler deploy` follows that pointer automatically, which is why no `--assets` flag
is needed anywhere. `.wrangler/` is gitignored on purpose — it contains machine-specific
paths and must be regenerated by each build.


## Verify before you push

The deploy is reproducible locally. This resolves the real config and bundles
everything without uploading anything:

```bash
npm run build
npx wrangler deploy --dry-run
```

Check that it reports the assets directory as `dist/client` and lists the `ASSETS`
binding. If that passes, the Cloudflare build will behave the same way.

To exercise the Worker itself, including the CMS sign-in gate:

```bash
npm run preview          # build + wrangler dev
```

## Secrets

The CMS OAuth credentials are Worker secrets, never files in the repo:

```bash
npx wrangler secret put GITHUB_CLIENT_ID
npx wrangler secret put GITHUB_CLIENT_SECRET
```

They attach to the Worker named in `wrangler.jsonc` (`cyberisrael-website`). For local
runs, copy `.dev.vars.example` to `.dev.vars`, which is gitignored. Only those two names
are needed; see [articles.md](./articles.md) for the OAuth app setup and how to verify the
access check.


## If something looks wrong

**Connect to Git only once.** Repeating the "Connect to Git" flow creates an additional
Worker rather than reconfiguring the existing one. That is how this project ended up
with several near-identical Workers, only one of which actually served the domain —
which in turn is why production briefly tracked a branch other than `main`. Before
creating anything in the dashboard, check whether a Worker with that name already
exists.

**The Worker that matters is the one holding the custom domain.** A deployment can
succeed on a duplicate Worker and change nothing on the live site. Confirm which Worker
`cyberisrael.net` is attached to under Settings → Domains & Routes.

**Production not updating after a merge?** Check that the production branch is still
`main`, and that the build ran the Deploy command rather than the Version command.
